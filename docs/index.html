03Why i8_ring

On this checkpoint the fast E4M3 PCIe-DMA wire modes (ag/ring) recover prefill speed but corrupt deep-context needle retrieval past ~300k. The needle-safe bf16 wire is correct but ~25% slower. Block-INT8 i8_ring delivers E4M3-ring-level prefill (~1,660 tok/s @ 50k) and keeps full-depth retrieval to 475k — you no longer have to trade speed for correctness.

04Use it

Public image on GHCR (digest-pinned):

docker pull ghcr.io/yatesdr/glm52-serve@sha256:ca8481687f7169adf177f02df83c06259af0941e9a1de8695b5a4e60d745463a
# or by tag
docker pull ghcr.io/yatesdr/glm52-serve:gilded-gnosis-v19-int8-block-patched

Key serving flags (see the full compose in the repo):

--kv-cache-dtype nvfp4_ds_mla          # + env KV_FP8_ROPE=1  → 368 B/token
--tensor-parallel-size 4 --decode-context-parallel-size 4
--dcp-comm-backend a2a --attention-backend B12X_MLA_SPARSE
--gpu-memory-utilization 0.970 --max-model-len 480000 --max-num-seqs 16
# env: B12X_PCIE_DMA_FP8=i8_ring  VLLM_PCIE_DMA_FP8=i8_ring
Interim (pre-v20) image. Baked patches PR #44/#46/#133 are validated. A known v19 async-cuBLAS concurrency hazard (independent of the wire mode) is not fixed in this image — it is covered operationally by a healthcheck + autoheal watchdog (~90 s recovery). The full fix (PR #132/#47) lands in v20. The NVMe secondary offload tier is deferred pending bounded disk eviction.
Hardware: 4× RTX PRO 6000, PCIe, no NVLink. All numbers measured with the standalone LIL inference bench; "baseline" = the same config's prior validated i8_ring run. Prefill "vs stock v19" compares against the needle-safe bf16 wire (~1,327 tok/s @ 55k, server-side) and is approximate (different measurement paths).
