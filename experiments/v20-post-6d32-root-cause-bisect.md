# v20 deep-retrieval regression: post-6d32 source bisect

Date: 2026-07-25  
Status: safe-query and #171 refuted end-to-end; SYS/PXB control in progress

## Field boundary

The regression is not a single monotonic “v20 cannot retrieve” result:

- image `6d32a0c3…` cold-retrieved the exact ticket at 50k and 250k;
- its 350k run exhausted an earlier 3,000-token response budget and was
  inconclusive;
- its 475k run retrieved in the reasoning field but did not finalize content;
- image `fa71a0c1…` fails 12/12 at 100k and above under cold and warm
  prefixes and multiple prompt-head constructions. A finer 60k–67k sweep is
  a degradation band rather than a hard point transition.

The newer image therefore introduced a real onset regression, while the older
image still had a separate finalization/deepest-context defect.

## Candidate 1 — PR #171 verifier route

Before #171, `auto` selected the split-K decode verifier for genuine MTP
batches. #171 changes `nvfp4_ds_mla` to single-pass extend while retaining
split-K decode for `fp8_ds_mla`.

The coverage does not justify that policy:

- the added test proves route selection only;
- the cited numerical causality test exercises `fp8_ds_mla`, not
  `nvfp4_ds_mla`;
- there is no NVFP4/DCP4 numerical oracle for the newly selected extend path.

This remains a valid residual old-v20 concern, but it is not selected for the
post-6d32 onset. A no-#171 diagnostic branch retaining the later memory/query
work is ready:

```text

head b8534c4a5fad9500c0aebd0ef5e293672033fc4e
```

Model-free discriminator:

```text

sha256 9a4a66a22bc063a84b1593ff6c7b4fc634bd513007988bddb32d42efc70097d0
```

It writes valid 368-byte NVFP4/FP8-RoPE records at physical depths
corresponding to 100k–475k global DCP4 context and compares split-K decode and
single-pass extend to the same explicit record oracle.

The no-#171 image booted with a measured 500,992-token pool, disproving the
488,784 forecast, but its first cold 100k causal row still missed:
`cached_tokens=0`, two completion tokens, `finish_reason=stop`, acceptance 0,
empty content, `reasoning="The"`. PR #171 is therefore not the cause of the
post-6d32 onset and is not selected as its fix.

## Candidate 2 — safe-query BMM compute mode

vLLM `992b874cf` changed:

```text
CUBLAS_COMPUTE_32F_PEDANTIC -> CUBLAS_COMPUTE_32F
```

The intent was to make tensor-core kernels eligible at production prefill
shapes. The change is numerically observable by design, but its test allows
`rtol=0.05, atol=0.05` before the result crosses a static FP8 quantizer. It
does not test:

- exact post-quantization bytes;
- downstream selected retrieval IDs;
- long-context model quality.

Our later staged BF16-to-FP8 guard does not restore the old operation. With
`VLLM_B12X_ABSORB_BMM=0` and compact quantized KV, the current route is:

```text
new regular-FP32 safe BMM -> concat -> static FP8 quantization
```

## Prepared accurate-reduction patch

```text
workspace/vllm-v20-safe-query-accurate-clean
branch fix/v20-safe-query-accurate-reduction-clean-20260725
head 0eb51f992
base 83a1f7f7d (build/gilded-gnosis-v20-dcp-final-20260725)
```

The patch does not revert the tensor-core compute type:

- regular FP32/tensor-core BMM remains the default;
- a BF16 absorbed query immediately consumed as quantized backend input keeps
  `CUBLAS_COMPUTE_32F` but forbids output-type intermediate reductions with
  `CUBLAS_MATH_DISALLOW_REDUCED_PRECISION_REDUCTION`;
- the incoming cuBLAS handle math mode is restored after every call, including
  the GEMM-error path;
- the old three-argument operator schema remains compatible;
- regular and precise CUDA-graph replay are both parameterized in tests;
- a missing precise CUDA op fails closed instead of silently changing bytes.

## Selected next step

1. Treat both the safe-query compute mode and PR #171 as refuted for this
   regression; neither causal rewind repaired cold 100k.
2. Resolve the newly discovered environment confound with a same-image,
   one-variable `NCCL_P2P_LEVEL=SYS` control. The known 6d32 cold-250k pass
   predates PXB; all current failures used PXB.
3. Require effective process environment, identical prompt hashes/seeds,
   `cached_tokens=0`, and three exact 100k rows before extending the ladder.
4. In parallel, trace the remaining 6d32→fa71 executable source delta,
   beginning with runtime reachability of the staged/fused MLA query plumbing.
5. Do not boot stock `5517197` or another source rewind until the transport
   control is conclusive.

## Fallback map if the precise build still fails

The remaining post-6d32 runtime deltas are already ranked:

1. New fused-query plumbing. The current BF16-to-FP8 guard should make it
   unreachable in this configuration; add runtime route counters to prove
   that before treating it as causal.
2. CUDA-graph capture-size policy. Compare eager/captured bytes for the same
   descriptor; do not infer from a model-quality A/B.
3. MRV2 graph-pool reuse, CKV profile initialization, NVMe bounds, and
   absorbed-weight release are memory/lifetime changes. They remain lower
   priority unless a byte/state probe shows live-buffer aliasing.

This ordering avoids another ladder of speculative 20–30 minute boots.

## Small-query route disposition

The upstream #174 fused BF16-to-FP8 route is more often exact against the
explicit reference, but a 90-case two-image CN4 probe measured it at about
twice the end-to-end current-stream cost of the staged M<=32 route. It cannot
address the long-prefill discriminator because its implementation limit is
M<=32. The production candidate therefore keeps the downstream staged-query
guard; #174 is a separate accuracy/performance decision and is not bundled
with the large-M reduction fix.
